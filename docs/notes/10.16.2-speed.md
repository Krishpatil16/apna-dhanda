## What changed
1. site/admin.js (257 KB, one big closure) is now BUILT into two files by tools/build-admin.mjs (esbuild minify + a split):
   - admin-core.js: everything the first screens need — Today (kirana + salon appointments/queue), Orders, bill, item edit inside an order,
     🔔 notifications, login / sign-up / setup, the shop bar. 94 KB raw, 31 KB on the wire (was admin.js: 257 KB raw, 74 KB on the wire).
   - admin-more.js: 41 rarely used functions — Settings, Items/catalog editor (product + service forms), salon catalogue, Stock screen
     (stock-in, limits, ready-list picker, Excel/PDF importer), Categories, Offers, Reports, Recharge/plan, History, Help, shop-type change,
     QR poster, Add-to-home-screen sheet, recovery-key screen. It loads the first time one is opened, and also quietly ~1 s after the page
     has loaded, so normally it is already there when the owner taps. 130 KB raw, 38 KB on the wire, cached a year.
   - Each moved function keeps its exact body (a test proves it byte-for-byte). Inside admin-more.js, names from the panel's closure are read
     through a live getter/setter object, so the moved code sees and changes the same variables. In admin-core.js each moved function is a
     stub with the same name: a plain call once admin-more.js is here, else "load it, then call".
   - If admin-more.js cannot be downloaded (no net), the tap shows the app's usual "Network problem. Please try again." toast; the next tap retries.
   - site/admin.js stays the readable source of truth (all old tests read it). After editing it run `node tools/build-admin.mjs`
     (also `npm run build`; `npm run deploy` runs it). npm test fails if admin-core.js / admin-more.js are stale.
2. Today's two reads start with the page: new admin-boot.js (0.7 KB, async in <head>) reads the login state the page already preloads and,
   for a logged-in owner opening Today, starts /api/admin/dashboard and /api/admin/orders?status=active&q= at once (before, they waited for
   ~160 KB of scripts). common.js api() hands each early answer to the first matching call (once, within 20 s; a call for one of those two
   waits until admin-boot.js has decided, so nothing is asked twice). Logged out, must-change-password, other hashes and God Mode viewing
   (/dev/as/…) start nothing extra.
3. Versions: APP_VERSION and SW_VERSION 10.16.2; every ?v= is 10.16.2, and common.js + admin-boot.js are ?v=10.16.2-2 (changed in the
   second upload, so no phone keeps the first copy). _headers: admin-core.js, admin-more.js, admin-boot.js cached a year (always asked with ?v=).
4. Not changed: every other page's files, all CSS, icons.js, the worker's API code. Static files were already served brotli-compressed by
   Cloudflare (that was not the problem: admin.js was 74 KB on the wire, 257 KB to parse).

trace): the network floor is HTML 0.45 s + one round trip 0.4 s + ~100 KB of shared files at 1.6 Mbps (two CSS files 29 KB, icons.js product-
icon catalogue 17 KB, common.js 12 KB, admin-core 31 KB …) ≈ 1.4 s, then ~0.4 s of 4×-slowed CPU (parsing scripts, icons.js building its
index ~130 ms, layout/paint). Getting to 1.5 s would need changing those shared files (CSS split, icons catalogue on demand), which touch
every page and the look of first paint — not done in this pass.
